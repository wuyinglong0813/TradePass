审查项 **1–8 均已完成代码修复**。第 5 项在用户追加授权后关闭了生产体验账号特权初始化；其他优化建议保持原状。验证使用本地测试和独立 MySQL 测试库；未部署生产环境，尚未清理线上数据。

## 修复结果

| 审查项 | 修复后的行为 | 主要验证 |
| --- | --- | --- |
| 1. 无权限用户终止第三方签署 | 撤回、拒绝统一由 TradeService 校验权限、合同归属和状态并锁定合同，再调用第三方取消；确认第三方已终止后才变更本地状态。远端已成功、本地回滚后的重试先查询远端状态。 | 无权限、其他企业、取消未确认、已经签完、远端取消成功后重试 |
| 2. 旧回调污染新版合同 | 创建签署任务时保存合同快照；修改前先终止旧任务。回调锁定合同和任务，只处理相同版本；归档使用签署快照，生效和作废更新同时约束版本、状态。 | 旧版本回调、快照版本错误、重复完成、已撤回合同、同步返回新状态 |
| 3. 多行同商品退货 | 按商品 ID 合计退货数量，再验证库存并扣减一次；单据明细及收方入库明细保留原有多行。 | MySQL 实测：库存 10、退 3+4，出方剩 3、收方入 7；退 6+6 整笔回滚 |
| 4. 撤回与确认覆盖状态 | 撤回、确认/入库、编辑、发布、删除和作废冲销共同使用单据行锁；库存、接收记录、对账与状态共用事务。 | 两个真实数据库连接分别验证双方先提交的情况；只允许先执行成功的一方生效；重复确认只入账一次 |
| 5. 生产默认启用体验账号特权 | `prod` 中 `experience-test-accounts.enabled` 固定为 `false`，不再读取旧的 `TRADEPASS_EXPERIENCE_TEST_ACCOUNTS_ENABLED` 变量。原体验手机号不会自动建企业、获得法人角色或模拟认证状态；本地 `dev` 能力保留。 | 加载真实生产配置，分别验证默认配置与旧变量为 `true`；两个原体验手机号都不会触发任何企业、角色或模板写入 |
| 6. 已认证资料直接改名 | 已认证/审核中的名称和法人姓名禁止直接修改；已认证资料维护要求当前法人权限；使用电子签身份时再次核对企业认证状态、名称和信用代码。 | 改名称、改法人、原创建者已失去法人角色、联系信息正常修改、缓存身份与当前企业不符 |
| 7. 多企业法人接受邀请绑错企业 | 只查当前所选企业的 ACTIVE 法人身份；拒绝本企业邀请。邀请码行锁与条件更新防止重复消费，关系创建失败会回滚。 | 同一法人有多个企业时限定当前企业、自己邀请自己、关系写入失败不消费邀请码 |
| 8. 回调失败无恢复 | 验签通过后先持久化必要路由/状态字段，再异步处理；数据库原子领取、5 分钟租约、完成令牌校验；失败按 30 秒起指数退避，最长间隔 1 小时持续重试。定时任务默认每 30 秒扫描；进程重启和异步派发失败可恢复。 | 失败后成功、重复请求、并发领取、租约超时、旧工作者不能覆盖新结果、回调早于业务记录提交、历史记录补齐负载 |

- 第 1、2、3、4、6、7、8 项修复后，后端全量 **225 项测试通过，0 失败、0 错误、0 跳过**，比审查基线新增 39 项；其中 8 项为真实 MySQL 集成测试。
- 追加第 5 项后，针对生产配置、体验账号与登录流程执行 **14 项测试，全部通过**，其中新增 2 项真实生产配置加载测试；未重复运行其余无关测试。
- 在独立数据库 `tradepass_fix_validation_20260902` 执行 V1–V24，插入旧格式回调记录，再执行 V25；25 个迁移全部校验通过，旧记录保留。
- 后端 JAR 成功生成，`git diff --check` 通过。
- `mvn verify` 最终仍因既有分支覆盖率门槛失败：本轮报告分支覆盖率 **47.34% / 要求 55%**；行覆盖率 **60.60% / 要求 60%**。没有调低门槛，也没有将其计作测试用例失败。
- 第三方接口通过网关替身覆盖成功、超时及失败路径，本轮未在真实服务商环境发起签署或企业认证。

## 发布时需要随代码执行的迁移

新增 `V25__signing_snapshot_and_callback_recovery.sql`，添加签署合同快照和回调恢复字段；用户后续要求取消自增 ID，又新增了 `V26__application_generated_ids.sql`。当前新版需要按 Flyway 流程升级至 V26；后端和小程序一起发布，详见 [ID 改造与完整重置](database-reset-and-ids.md)。

旧版本没有保存失败回调的业务负载，因此无法从 SHA-256 还原历史消息。旧的 FAILED/RECEIVED 记录在收到服务商重新签名发送的同一事件后，可补齐负载并进入重试；不能重发的记录需通过已有合同/认证同步入口核实业务结果。本轮没有改写已有生产数据，也没有伪造历史签署快照。

新建签署任务始终保存快照。升级前创建、没有快照的任务，仅在任务版本与当前合同版本一致时兼容生成归档元数据；版本不一致的历史回调不会修改现行合同。

## 重跑 MySQL 集成测试

先建立专用 `tradepass_fix_validation_*` 数据库。测试只允许连接这个前缀的数据库，会执行迁移、添加测试数据，并删除测试用户及权限字典以验证重新初始化。

```sh
mvn -pl backend \
  -Dtest=MysqlWorkflowConcurrencyTest \
  -Dtradepass.test.mysql.url=jdbc:mysql://127.0.0.1:1118/tradepass_fix_validation_20260902 \
  -Dtradepass.test.mysql.username=YOUR_TEST_USER \
  -Dtradepass.test.mysql.password=YOUR_TEST_PASSWORD \
  test
```

全量测试时去掉 `-Dtest=MysqlWorkflowConcurrencyTest`；后续 ID 改造将数据库测试扩充到 13 项，不提供数据库参数时默认跳过。当前全量后端 236 项、小程序 54 项测试均已通过；当前分支覆盖率 50.16%，仍低于 55% 门槛。

## 清空旧业务数据后重新验收

用户后续要求已落实：取消数据库自增 ID，程序自动补齐权限字典。清库时不再要求保留旧序号、权限字典或 Flyway 历史。先停止旧后端，然后按 [完整重置说明](database-reset-and-ids.md) 执行 [清表 SQL](../scripts/reset-for-online-retest.sql)，由新版从空库重建。

当前没有清理本地或线上业务数据。脚本仅处理本项目数据库表；云存储对象与法大大侧已有记录不在数据库清理范围内。
