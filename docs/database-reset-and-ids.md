# 应用生成 ID 与完整重置

本次修改取消了“为了继续使用旧 ID 序列而保留数据”的要求。新建记录使用应用生成的 Snowflake ID；数据库仍以 BIGINT 存储，但不再负责分配序号。清空数据库不会把 ID 重新从 1 开始分配。

## 代码变更

- 实体改用 `ASSIGN_ID`；所有 JDBC 写入显式传入主键，移除了 `LAST_INSERT_ID()`。两条写入路径共用 `IdentifierConfiguration` 配置的生成器。
- V26 删除当前 39 张业务表主键的 `AUTO_INCREMENT` 属性。普通升级保留已有行及关联值；选择完整重置时则全部重建。V1–V25 的历史迁移文件未因本次 ID 改造而改写。
- 接口把 `Long/long` 序列化为字符串。小程序合同列表、审批列表、模板列表、往来企业合同和发起合同不再把 ID 转成 JavaScript 数字，避免 19 位 ID 丢失精度。金额、页码和普通整数不受此规则影响。
- `SystemPermissionInitializer` 每次启动幂等补齐 18 项权限字典。生产关闭演示数据和体验手机号特权；用户、企业从正常注册认证流程创建，企业角色和模板在认证通过后初始化。

生成策略使用 MyBatis-Plus 提供的 Snowflake 实现，见 [官方 ID 生成器说明](https://baomidou.com/guides/id-generator/)。单实例未配置节点编号时由框架推导；多实例、滚动发布有新旧实例并行时，必须保证每个并行实例使用不同的 `(datacenter-id, worker-id)` 组合，两个编号均为 0–31。可通过 `TRADEPASS_IDS_DATACENTER_ID` 与 `TRADEPASS_IDS_WORKER_ID` 一起设置，不能让所有并行实例使用同一组值。服务器时钟应保持同步，不能靠回拨时间来重置 ID。

## 本次从空库重新验收的顺序

1. 备份需要保留的内容，并停止所有旧后端实例，避免清表时仍有请求或回调任务写入。
2. 在数据库客户端选中要清空的 **TradePass 专用数据库**，执行 [`scripts/reset-for-online-retest.sql`](../scripts/reset-for-online-retest.sql)。脚本列出当前项目的全部 42 张表，包含业务数据、登录会话、回调事件、权限字典及 Flyway 历史表，并删除这些表。
3. 启动包含 V26 的新版后端。Flyway 从 V1 执行到 V26 重新建表，程序补齐权限字典。无须手动重建权限、恢复序号或创建体验账号。
4. 如果开启了 Redis，切换到新的 `TRADEPASS_REDIS_KEY_PREFIX`，让旧登录缓存和统计缓存失效；默认未开启 Redis 时无需这一步。
5. 发布本次修改的小程序，退出旧登录后重新进入，按注册、企业认证、邀请合作、签署、单据确认和退货流程验收。

此流程无需保留任何旧表。`flyway_schema_history` 必须与其他项目表一并删除，不能只清空它的记录却留下旧表结构，否则启动时会重复执行迁移。

清表 SQL 不删除数据库账号和连接配置，也不会删除云存储里的文件或法大大侧的认证、签署任务、已签文件。如还需要清理云文件，先保存对象清单，再清数据库。历史第三方回调可能继续到达；新用户及企业 ID 不会因数据库清空而重新采用旧自增值。
